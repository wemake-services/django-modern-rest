# Upgrade django-modern-rest from 0.16.0 to 0.17.0

Source: `CHANGELOG.md`, release `0.17.0`
(https://github.com/wemake-services/django-modern-rest/releases/tag/0.17.0),
and the API of the `0.17.0` git tag. The GitHub release notes list the
breaking changes; this prompt expands them against the tagged sources,
it is not a verbatim copy of the release page.

Read this file only while upgrading across this release. Apply every item,
search the whole project (including tests and fixtures) for each one.

## Prompt

You are migrating a Python project from `django-modern-rest` 0.16.0 to 0.17.0.
Load the documentation for the target version, `llms.txt` lists every page:
https://django-modern-rest.readthedocs.io/en/0.17.0/llms.txt
If that version of the documentation is not available, read the sources and
docs of the `0.17.0` git tag, not `master`.

Apply **all** of the following breaking changes to the codebase.
For each change, search the entire project (including tests, fixtures, and
any helper modules) before editing.

---

### 1. Use `EMPTY` in DMR sentinel annotations

`django-modern-rest` 0.17.0 replaced `typing_extensions.Sentinel` in all of
its public annotations with its `EMPTY` sentinel value. Code that copied
the old annotations or detected the DMR "not set on this level" marker
through `Sentinel` must switch to `EMPTY`.

Find every DMR setting, controller attribute, endpoint parameter, and
metadata field annotated with `Sentinel`, and every runtime check that used
`isinstance(value, Sentinel)` to detect an unset DMR value:

Before:
    from typing import ClassVar

    from typing_extensions import Sentinel

    from dmr.types import EMPTY

    class MyController(Controller[Serializer]):
        validate_responses: ClassVar[bool | Sentinel] = EMPTY
        auth: ClassVar[Sequence[SyncAuth] | Sentinel | None] = EMPTY

    if isinstance(controller.validate_responses, Sentinel):
        ...

After:
    from typing import ClassVar

    from dmr.types import EMPTY

    class MyController(Controller[Serializer]):
        validate_responses: ClassVar[bool | EMPTY] = EMPTY
        auth: ClassVar[Sequence[SyncAuth] | EMPTY | None] = EMPTY

    if controller.validate_responses is EMPTY:
        ...

Replace `bool | Sentinel` with `bool | EMPTY`, including inside
`ClassVar[...]`, `Sequence[...]`, and unions with `None`. Import `EMPTY`
from `dmr.types`.

Replace `isinstance(value, Sentinel)` with `value is EMPTY` when the check
means "did the project set this DMR value". `EMPTY` is a singleton and must
be compared by identity, not equality, and `isinstance(value, Sentinel)`
also accepts sentinel objects that have nothing to do with DMR.

Remove the `Sentinel` import only when nothing else in the module uses it.
Do not replace `None`: it still means an explicit "off" value on many DMR
settings. Do not replace the project's own sentinel objects either.

Check `dmr/controller.py` and `dmr/types.py` in the `0.17.0` tag, and
PR https://github.com/wemake-services/django-modern-rest/pull/1687.

### 2. Use `TypeForm` for type-valued extension parameters

0.17.0 changed DMR extension points that accept a **type expression** from
`Any` or `type[Any]` to `TypeForm[Any]` (PEP 747). A type expression is
an annotation object like `Model`, `Model | None`, `list[Model]`, or
`Literal['first', 'second']`, not a runtime payload or a DTO field value.

Find overrides of the DMR extension points that receive a model or
annotation and update only the parameters that the new base contract
changes:

Before:
    from typing import Any

    from django.http import HttpRequest

    from dmr.parsers import DeserializeFunc, Parser, Raw

    class MyParser(Parser):
        def parse(
            self,
            to_deserialize: Raw,
            deserializer_hook: DeserializeFunc | None = None,
            *,
            request: HttpRequest,
            model: Any,
        ) -> Any:
            ...

After:
    from typing import Any

    from django.http import HttpRequest
    from typing_extensions import TypeForm

    from dmr.parsers import DeserializeFunc, Parser, Raw

    class MyParser(Parser):
        def parse(
            self,
            to_deserialize: Raw,
            deserializer_hook: DeserializeFunc | None = None,
            *,
            request: HttpRequest,
            model: TypeForm[Any],
        ) -> Any:
            ...

The affected boundaries include:

- `BaseSerializer.deserialize` and `BaseSerializer.from_python`.
- `BaseSchemaGenerator.get_schema` and `BaseSchemaGenerator.schema_name`.
- `ComponentParser.provide_context_data(field_model=...)` and
  `ComponentParserSpec.model`.
- `FileBodyLike.media_type(model=...)`.
- `ContextField.annotation` and `ContextModel.model`.
- `ResponseSpec.return_type`.
- `Controller.error_model`.

Update an override only where the new base signature requires it. Do not
mechanically replace every `Any` in payload models, DTO fields, endpoint
return values, or unrelated helper functions.

`Model | None`, parametrized generics like `list[Model]`, and `Literal[...]`
are all valid type expressions. `type[Any]` is not equivalent: it accepts
only classes, not unions, generics with arguments, or `Literal` values.
Do not add `cast` to silence a type-checker error; pass the actual type
expression instead.

Other signatures changed in the same release, see
https://github.com/wemake-services/django-modern-rest/pull/1688/files.

### 3. Consume the CSRF scheme mapping

`dmr.security.csrf.csrf_security_scheme()` used to return a single
`SecurityScheme`. It now takes the scheme names and returns a mapping
of schemes:

    csrf_security_scheme(
        scheme_name: str,
        header_scheme_name: str,
    ) -> dict[str, SecurityScheme | Reference]

Cookie mode returns two entries, the CSRF cookie and the CSRF header.
`CSRF_USE_SESSIONS = True` returns only the header entry.

Find every call of `csrf_security_scheme()` and update it. When the mapping
is merged with other security schemes, unpack it. Do not wrap it in another
dictionary under a single key:

Before:
    from dmr.security.csrf import csrf_security_scheme

    security_schemes = {'csrf': csrf_security_scheme()}

After:
    from dmr.security.csrf import csrf_security_scheme

    security_schemes = {
        **csrf_security_scheme(
            scheme_name='csrf',
            header_scheme_name='csrf_header',
        ),
        # ...other auth schemes...
    }

`CSRFAuthMixin.csrf_security_scheme(self)` still takes no arguments and now
returns the same mapping. Update every override of it. Own subclasses of
the mixin must also set `csrf_header_scheme_name`, next to the existing
`security_scheme_name` and `csrf_scheme_name` attributes.

The session auth, the cookie JWT auth, and the cookie token auth, both sync
and async variants, accept `csrf_header_scheme_name=` in their constructors.

`CSRFSemanticSchemaProvider` names its field `security_header_scheme_name=`,
next to `security_scheme_name=`. The attribute list in its docstring spells
the field `csrf_header_scheme_name`; do not copy that name into code.

The keys of the returned mapping become `components.securitySchemes` keys.
They must not collide with the project's own auth scheme keys.

Source: `dmr/security/csrf.py` and
https://github.com/wemake-services/django-modern-rest/pull/1718.

### 4. Update OpenAPI CSRF requirements

The generated security requirements changed with the same release. Before,
cookie mode published one `csrf` requirement for the cookie, and session
mode reused the `csrf` key for the header scheme.

- For CSRF-protected unsafe operations in cookie mode
  (`CSRF_USE_SESSIONS = False`), put `csrf` (the cookie named by
  `CSRF_COOKIE_NAME`) and `csrf_header` in the same security requirement
  as the corresponding auth scheme, when there is one. All schemes in
  that object must be sent together:

      [{'django_session': [], 'csrf': [], 'csrf_header': []}]

- In session mode (`CSRF_USE_SESSIONS = True`), the only CSRF key is
  `csrf_header`; there is no separate `csrf` key. Keep any corresponding
  auth scheme in the same requirement:

      [{'django_session': [], 'csrf_header': []}]

- An unauthenticated route protected by CSRF middleware may instead have
  a CSRF-only requirement: both keys in cookie mode, or only the header
  key in session mode. Safe methods (`GET`, `HEAD`, `OPTIONS`, `TRACE`)
  receive no additional CSRF requirement.

The header scheme names the HTTP header derived from `CSRF_HEADER_NAME`,
not the raw Django `META` key (for example, `HTTP_X_CSRFTOKEN` becomes
`X-CSRFToken`). Preserve separate OR alternatives in the security array
and add CSRF only to the alternatives and operations it protects; do not
add it to unrelated Bearer-only operations.

When the project customizes scheme names, use the configured names. Check
existing `exclude_semantic_auth` filters: to hide both CSRF schemes from
auth providers in cookie mode, exclude both configured CSRF keys; in
session mode exclude the header key. This filter applies to auth providers,
not universally to `CSRFSemanticSchemaProvider`.

Update OpenAPI snapshots, hand-written `security` requirements, and
generated clients. Do not add duplicate built-in schemes or change
`CSRF_USE_SESSIONS`, `CSRF_COOKIE_NAME`, `CSRF_HEADER_NAME`, or runtime
CSRF checks to make the schema match.

Source: `dmr/security/csrf.py` and
`tests/test_unit/test_security/test_django_session_auth.py` in the
`0.17.0` tag,
https://github.com/wemake-services/django-modern-rest/pull/1718.

## Conditional behavior checks

These are behavior changes, not mechanical renames. Check each one only
when the project uses the affected feature. When it applies, fix the
project or report the decision to the user.

### `BodyMsgspec` requires model-decoding parsers

`BodyMsgspec` now raises `EndpointMetadataError` at import time when at
least one effective parser does not decode directly into the model.
`MsgspecJsonParser()` and `MsgpackParser()` set `decodes_into_model`;
`JsonParser()` and the form parsers do not.

If the endpoint must keep its existing parsers or media types, use
`Body[...]` for that endpoint instead of `BodyMsgspec`. Do not drop a parser
just to keep `BodyMsgspec`.

A custom parser may set `decodes_into_model = True` only when it returns a
validated model instance, raises `msgspec.ValidationError` when decoded
data does not match the model, raises `DataParsingError` for malformed
encoding or syntax, and treats empty bytes as `None` validated against the
model. This is the contract documented on `dmr.parsers.Parser`.

Source: `dmr/parsers.py`, `dmr/plugins/msgspec/json.py`, and
`dmr/plugins/msgspec/components.py`.

### `FileMetadata` requires file-parsing parsers

For a required `FileMetadata[Model]`, every effective parser must implement
`SupportsFileParsing`. For an optional
`FileMetadata[Model | None] = None`, at least one parser must. The old
check used `any()` for both cases; a mixed set of parsers now fails at
import time for the required form.

Do not make a required upload optional just to pass the check. When the
endpoint negotiates formats where some parsers cannot parse files, keep the
contract: restrict the parsers for that endpoint, or split the file
endpoint from the endpoint that accepts the other formats. Tell the user
when the routes have to be split.

Source: `dmr/components.py`, `FileMetadataComponent.validate`.

### `wrap_middleware` validates the short path

The middleware response's status **before** conversion must be among the
statuses configured on the decorator (for example, `302` for
`login_required`). The converted short-path response is then validated like
an endpoint response. For example, if the converter changes `302` to `401`,
document and validate the final `401`, its `Content-Type`, headers, and body
against the effective endpoint `ResponseSpec`s. With `validate_responses`
on, an undocumented final status or a response that does not match its
spec can produce `422`.

A conditional middleware response such as `304` often has no `Content-Type`.
Add a supported `Content-Type` in the converter: a missing one can cause
`KeyError`, not an ordinary `422`. Exercise conditional responses,
including the async wrapper where used. Fix the converter and document the
actual final response; do not disable `validate_responses` or exclude a
status to hide the failure.

Source: `dmr/decorators.py`, `dmr/internal/middleware_wrapper.py`,
`dmr/validation/response.py`, and
`docs/examples/middleware/built_in_decorators.py`.

### OpenAPI output changes

Regenerate the schema and generated clients, then check:

- A response spec whose return type is `None` no longer has a `content`
  object. This does not apply to a `Model | None` response spec.
- Login `concrete_views` no longer inherit `OpenAPIConfig.security`: they
  set `security = None`. Do not assume the operation is public or has no
  CSRF requirements: CSRF or custom requirements may still apply.
- `Retry-After` and `X-RateLimit-*` throttling headers are documented as
  integers with examples. This changes the OpenAPI type only; the HTTP
  header value is still a string.
- Building a schema for a `Query`, `Headers`, `Path`, or `Cookies` model
  containing a `$ref` outside `#/components/schemas/` no longer raises
  the former `KeyError`. That does not mean the external reference is
  resolved. Before removing any workaround, inspect the generated parameter
  lists and confirm they still contain the required parameters.

### Cookie JWT expirations

When `as_view()` of a cookie JWT `concrete_view` receives
`jwt_expiration=` or `jwt_refresh_expiration=`, pass them explicitly and
compare the token lifetime with the cookie `Max-Age` for obtain and refresh
responses. They are typed `as_view` arguments now and set on the class, so
the values match. Logout drops cookies with `Max-Age=0` and is not part of
that comparison. If the project relied on the old mismatch, decide which
lifetime is correct and set it explicitly.

### `RateLimitIETFDraft` header format

`RateLimit-Policy` now follows the IETF draft: every policy is a quoted
name with `q` and `w` parameters, for example `"RemoteAddr";q=5;w=60`.
A policy name that is not unique among endpoint throttles using this
provider gets the window appended (`RemoteAddr-60`), and the number of
requests is appended too when the window is also the same. Check both
`RateLimit-Policy` and `RateLimit` headers, and update header parsers,
client code, and snapshots that match the old names or format.

With `SyncRedis` or `AsyncRedis` and `SimpleRate`, an empty current window
now reports the full interval instead of a negative `X-RateLimit-Reset`.
Check client backoff logic that treated the negative value specially.

For a custom throttling backend, check that `CachedRateLimit` is closed in
the `0.17.0` tag: backend-private keys must stay internal, and public
`get`/`incr` results must contain only the defined keys.

### i18n error handlers

`build_404_handler`, `build_500_handler`, and `build_csrf_handler` now
match a language prefix from `i18n_patterns`, for example
`/en/api/missing/`. Pass `languages=` to allow only exact languages; by
default all languages configured in Django are allowed. Verify the API
error response, not Django's HTML page.

### Streaming ping cleanup

With `Streaming(ping_seconds=...)`, closing or cancelling the stream now
cancels the pending event task. Verify that a client disconnect closes the
stream without `RuntimeError: aclose(): asynchronous generator is already
running` or a task failing on the already closed response.

### Optional features

Do not migrate to `BaseJWTokenHandler`, a newer Python version, or
`MsgspecSerializer.enable_component_gc` unless the project needs them.
They are additive features in 0.17.0, not part of this upgrade.

project. The upgrade is complete when no outdated form of the changed APIs
remains, not when every symbol mentioned above disappears from the project.
